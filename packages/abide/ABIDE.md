# Working on an abide app

These instructions ship with `@abide/abide` and update with it — do not edit this file.

abide is newer than any model's training data, so read its documentation before writing code,
rather than guessing from Svelte, Vue or React. It installs with the package:

- `node_modules/@abide/abide/docs/abide.md` — every documentation page in reading order, with a
  working example for each task. It is long: read its Contents, then search for the page's
  address, which heads each page as a comment — `<!-- guide/keep-it-current.md -->`.
- `node_modules/@abide/abide/docs/REGISTRY.md` — every name an app can import or write, with its
  signature and the rules that govern it.
- `node_modules/@abide/abide/docs/RULEBOOK.md` — every rule, numbered. A compiler or server
  message that ends in `RULEBOOK 23.16.` names a clause in this file — search it for `23.16`.

When abide itself misbehaves, do not code around it: leave a `TODO(abide):` comment above the
affected code saying what it did, and tell the user.

## Checking your work

- `bun run check` — runs `abide check`, the type checker over `.abide` files. `tsc` and an editor's
  TypeScript service do not read `.abide` files, so a clean `tsc` says nothing about them. Run
  `bun run check` after every change, and treat its warnings as bugs: several of them name a read
  that will not update when its value changes.
  Where the read is meant, `// abide-ignore` and the clause the warning cites, on the line above
  (`// abide-ignore 14.15`), silences that one (RULEBOOK 14.19); a read hoisted out of its place
  only to quiet a warning is the bug it named.
- `bun run test` — runs `bun test`. Every handler file has a test that imports the handler and
  calls it. Every component has a test that `mount`s it and counts the work an
  interaction did with `measure`, both from `@abide/harness/abide` (RULEBOOK 38.119, 43.23) — a
  test that only reads the text back passes against a component doing ten times the work.
  A test waits on a value landing — `await` the handler call, or the `Reactive` the component
  reads, which is thenable (RULEBOOK 1.4) — never on `Bun.sleep` or a timer. Break the code once and
  watch a new test fail; a test that has never failed has not been shown to test anything.
  Called outside a request, a `GET` keeps its answer for the whole test process: a test that changes
  the data behind one calls its `invalidate()` in `beforeEach`. A handler that reads `config()` or
  `principal` runs inside `app.run(…)` of `await createApp()`, where the app's `onConfig` has run.
  `mount` sets no route, so a page stays thin: it reads the route and hands what it needs to a
  component in `lib/`, and the test mounts that component.
- `bun run bench` — runs `harness-bench`: every `*.bench.ts` under `src/`, kept beside the code it
  times. Each export is a function returning `batch()` from `@abide/harness/report`, an op at two
  sizes; a `CEILINGS` export, `{ [bench]: { [arm]: milliseconds } }`, names the most each arm may
  take, and an arm over it, or a ceiling naming no bench or arm, fails the run (RULEBOOK 43.29,
  43.31, 43.32, 43.33).
- `bun run format` — `abide format` over every `.abide`, then `bun fmt` over the rest. Run it once
  your changes are done.
- `bun run dev` — serves the app on a local port and rebuilds when a file changes.
- `bun run build` then `bun run start` — the production build, and the app served from it.
- `docker build .` — the scaffold's `Dockerfile` runs `abide compile` and ships the one executable it
  writes on a distroless image, and nothing else of the app (RULEBOOK 38.132).

## Layout

- A file's path below `src/` is its address. `src/invoices/index.abide` answers `/invoices`,
  `src/invoices/[id].abide` answers `/invoices/123`, and `layout.abide` wraps the pages below it;
  the outermost one writes `<html>`. Run `bun run routes` to see every address and the file behind it.
- A `<name>.handler.ts` beside the pages is a handler: `src/invoices/getInvoice.handler.ts` holds
  `export default GET(…)` and answers `/invoices/getInvoice`. It is the app's public API, for pages,
  scripts, the CLI and MCP alike.
- A `.abide` cannot export. A `<script server>` in one holds that file's private handlers
  (`const save = POST(…)`), callable by that file alone, and its hooks (`onStart`, `middleware`, …).
- A rung shared between handlers or layouts is typed `Middleware` and nothing else:
  `export const signedIn: Middleware = async (next) => (await principal.authenticated) ? next() : refuse(401)`
  fits a handler's `middleware: […]` and a layout's `middleware(…)` alike (RULEBOOK 37.14). No
  `<Ctx, Result>` of its own, and no `as` on a `refuse`.
- A directory holds addresses, tests, benches, `.d.ts` declarations and two fenced directories
  alone: `lib/` for components and modules, and `public/` for files served as they are. Anything
  else beside the pages is a build error.
- Either fence may sit in any directory, at the root or beside the pages that use it.
  `src/lib/` and `src/invoices/lib/` import alike (`#src/…`); the one difference is a lifecycle
  hook a `lib/` file calls, filed at the route of the directory holding that `lib/` (RULEBOOK 37.1).
  A `public/` file answers at the route of the directory holding it: `src/public/logo.png` answers
  `/logo.png`, and `src/blog/public/cover.png` answers `/blog/cover.png`.
- Put a module in the `lib/` beside the pages that use it, and in `src/lib/` only once pages in
  different directories share it. Within a `lib/`, group by what the code is about (`cart/`,
  `catalog/`), not by which side runs it — the `.server.ts` name already says that.
- A test is a `.test.ts`, and a bench a `.bench.ts`, kept beside the file it tests or times — a
  page, a handler, or a module in `lib/` (RULEBOOK 23.22). There is no `tests/` folder.
  A browser test (playwright) is a `.test.ts` too, under `e2e/` beside `src/`: `bun test` reads
  `src/` alone (`root` in `bunfig.toml`), so it never runs one.
- A module the browser never loads is named `<name>.server.ts` and lives in `lib/`
  (`src/invoices/lib/db.server.ts`); importing one from browser code is a compile error. A module it
  imports is not fenced by it.
- Import the app's own modules as `#src/…` (see `imports` in `package.json`).
- A test imports `.abide` files directly: `bunfig.toml` preloads `@abide/harness/abide/preload`,
  a DOM to mount into and then `@abide/abide/test`.

## Reactive values

- Export a `Reactive` itself, never wrapped in an object — one per file, even when several belong
  together: an `.abide` file reads and writes it by name (RULEBOOK 31.1), and one reached through a
  property is left to `x()` and `x.set(v)` (31.7).
- Change part of a value by writing through its path — `edits.kind = kind`, `items.push(item)`
  (RULEBOOK 31.8, 31.9) — not by rebuilding it (`edits = { ...edits, kind }`,
  `items = [...items, item]`). Bind through the path too: `bind:value={edits.kind}` (32.5), not a
  `{ get, set }` pair. In a `.ts` file the same write is `edits.patch((value) => { value.kind = kind })`,
  not `edits.set({ ...edits(), kind })`.
- Derive a value with `reactive(() => …)`. `watch` is only for reaching outside the reactive graph —
  the DOM, a timer, an imperative API — and never assigns state; a user action's effect belongs in
  its event handler. A `watch` runs during a server render too (RULEBOOK 12.5), so one that starts a
  timer or touches a browser global returns a `Disposer`.
- A preference the page renders — a currency, a theme, a panel left open — lives in a cookie:
  `const theme = reactive(() => cookies().get('theme') ?? 'light')`, written with
  `cookies().set('theme', next)`. `cookies()` is the request's on the server and the document's in
  the browser, and a read by name is tracked (RULEBOOK 22.2, 22.4), so the first paint is already
  right and a write repaints. The browser sends it, so check what it holds before trusting it.
  `localStorage` is for a working set the browser alone needs: the server cannot read it, and
  renders the initial value.
- A value that has not landed leaves its place in markup as it was — empty before it first lands,
  the last value while it reloads — and fills it when it lands (RULEBOOK 32.23), so markup needs no
  guard. Do not paper over it with `?? []` or `x.ready() ? x : undefined`
  — that makes "not loaded yet" read as "empty". Branch on `x.ready()` or `x.busy()` only where a
  placeholder is actually wanted.

## Settings and untrusted input

- Settings come from `onConfig` and `config` (RULEBOOK 27.2, 27.9), and cookies from `cookies()`
  (22.2) — never `Bun.env`, `process.env` or a parsed `cookie` header in `src/`, and never a branch on
  `NODE_ENV`. The environment overrides a default `onConfig` returns (27.2, 27.8), and `bun test`
  reads `.env.test`, so a test's database or data directory is a line in `.env.test`, not a check in
  the app's code.
- Model output, markdown and fetched HTML are untrusted. Never hand them to `raw()` (RULEBOOK 32.2)
  unsanitized. Render markdown on the server — a component in the browser calls a private `POST` in
  its `<script server>` for it. `Bun.markdown.html(text, { noHtmlBlocks: true, noHtmlSpans: true })`
  escapes HTML but keeps a `javascript:` URL, so pass its output through `HTMLRewriter` and drop any
  `href` that is not `http:`, `https:` or `mailto:`, and any `src` that is not `http:` or `https:`.

## Measuring

- Measure with `@abide/harness`, not a hand-written timer, bench runner or Chrome DevTools Protocol
  script: `measure` in a test and `batch` in a bench (above), and `traceOp` and `shares` from
  `@abide/harness/engine` for what Chromium did, from a playwright test. The page
  `guide/test-measure-and-ship.md` in `abide.md`, and "The measurement harness" in `REGISTRY.md`,
  document it.

## Code

- One export per file, and the file is named after it: `SCREAMING_SNAKE_CASE.ts` for a constant,
  `TitleCase.abide` / `TitleCase.ts` for a component, a class or a type, `camelCase.ts` for a
  function. No barrel files. Before writing a helper, search `lib/` for one to reuse or widen.
  macOS disks ignore case, so two files in one directory never differ by case alone
  (`RecipeStore.ts` beside `recipeStore.ts`): one silently replaces the other.
- Names say what they hold — `selectedInvoice`, not `sel`, `x` or `S`.
- A file past a few hundred lines is a component or a module waiting to be split out; split it
  before adding to it.
- Use Bun's APIs (`Bun.file`, `Bun.write`, `Bun.$`, `bun:sqlite`) before `node:` ones.
- Style with tailwind classes. `style=` is for a value computed at runtime. Tailwind is wired
  already (RULEBOOK 38.131): `src/lib/app.css`, imported by the root `layout.abide`, is where a theme
  or a plugin goes.
- In code that runs per row, per frame or per chunk, write a `for` loop rather than a chain of
  `map` / `filter` / `reduce`, which allocates an array per step. Elsewhere, write what reads best.
- Comment only where the reason is not obvious from the code, in a line or two. A comment is not a
  log: no history ("used to…", "now…") and no file paths that go stale.
